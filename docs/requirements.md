## 1. プロジェクト概要

### 1.1 目的

スマートフォンで撮影したレシート画像から、記載内容を文字起こしし、**レシート全体のジャンル**と**品目ごとのジャンル**を自動で仕分けして、Webブラウザ上に表示する。

### 1.2 誰の、何のためのアプリか

- **対象ユーザー**: 家計の支出を手軽に分類したい個人（本課題では開発者自身）
- **解決したい課題**: レシートを手入力で仕分ける手間をなくす
- **位置づけ**: 機械学習コース最終課題。規模や完成度より、「データ準備 → モデル開発 → アプリ組み込み → デプロイ」を一貫してやり切ることを重視する

### 1.3 基本方針

1. **画像を扱うのは最初の段階だけ**にし、以降はOCR結果（テキスト＋座標）を対象にする
2. **多段パイプライン**にし、段ごとに評価できるようにする（原因の切り分けと、スライドでの説明のしやすさのため）
3. **自前コードで動くモデルが主、外部APIは補助**（修了要件①）
4. **DGX Sparkは学習・実験・教師データ作りに使う**。提出用デプロイは別途検討（§11）
5. **個人情報を公開物に含めない**（§12）

## 2. 修了要件との対応

| 修了要件 | 本アプリでの充足方法 | 状態 |
|---|---|---|
| ① 機械学習モデルの構築・活用 | OCR・行分類・店ジャンル分類・品目ジャンル分類を、transformers等で読み込み自前の推論コードで実行する。分類系は自前データでファインチューニングする | 設計済み |
| ② ユーザーが操作できるフロントエンド | Phoenix（LiveView）製のWeb UI。画像アップロード→結果表示を画面操作のみで完結 | 設計済み |
| ③ デプロイされ一連の動作が確認できる | 常時公開URLで「入力 → 推論 → 結果表示」が動くこと | **【要確認】** §11 |

**注意点**

- OllamaやvLLMなどの配信サーバー経由でモデルを呼ぶ構成は、要件文言とずれて見える可能性がある。**モデルのロードと推論コードはリポジトリ内のPythonで記述する**
- 外部API（検索など）は「要件を満たすモデルとは別の補助機能」としてのみ使う。**ジャンル判定の本体を外部LLM APIに任せない**

## 3. スコープ

### 3.1 対象範囲（In Scope）

- 日本語の店舗で発行されたレシートの画像入力（スマホで比較的正面から撮影したもの）
- レシート領域の抽出・補正、OCR、行の役割分類、品目の項目抽出
- 店名からの店ジャンル判定（検索＋自前分類モデル）
- 品目ごとのジャンル判定
- 結果表示、および低信頼時のユーザー選択UI
- 学習データ作成・学習・評価の一連のスクリプト／ノートブック

### 3.2 対象外（Out of Scope）

- 家計簿としての保存・集計・グラフ化
- ユーザーアカウント、ログイン、履歴の永続化
- 手書き領収書、海外レシート、極端に斜めや折れ曲がった画像
- スマホネイティブアプリ

### 3.3 将来拡張（時間に余裕がある場合のみ）

- JANコードによる品目判定の併用（外部商品DBが必要なため後回し）
- ユーザーの修正結果を再学習データとして蓄積する仕組み
- 画像→JSONを一発で出す視覚言語モデル方式との比較実験（DGX Spark上）
- OCRモデルのファインチューニング（素のOCRで誤読パターンを見てから判断）

## 4. 機能要件

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| FR-01 | 画像アップロード | スマホ撮影画像（JPEG/PNG/HEIC→変換）をブラウザから送信できる。サイズ上限あり | 必須 |
| FR-02 | レシート領域抽出 | OpenCVの輪郭検出と射影変換で、レシート部分を切り出し・補正する。失敗時は原画像で続行 | 必須 |
| FR-03 | OCR | 補正後画像から、行ごとのテキストと座標を取得する | 必須 |
| FR-04 | 行の役割分類 | 各行を「店名／日付／品目／小計・合計／支払い／その他」に分類する | 必須 |
| FR-05 | 品目の項目抽出 | 品目行から「項目名・個数・単価・金額」を抽出する（ルール中心、崩れる分だけモデルで補う） | 必須 |
| FR-06 | 整合性チェック | 品目金額の合計と、合計金額が一致するかを自動判定し、結果をUIに表示する | 必須 |
| FR-07 | 店名正規化 | 「株式会社」「〇〇店」等を除去し、検索用の店名に整形する | 必須 |
| FR-08 | 店情報の検索 | 店名のみを検索クエリとして外部検索を呼び、店の概要テキストを取得する | 必須 |
| FR-09 | 店ジャンル分類 | 概要テキストを自前の分類モデルで店ジャンルに分類し、信頼度を出す | 必須 |
| FR-10 | 判定粒度の決定 | 店ジャンルから「全体で1ジャンル」か「品目ごとに判定」かを対応表で決める | 必須 |
| FR-11 | 品目ジャンル分類 | 品目名を自前の分類モデルで品目ジャンルに分類し、信頼度を出す | 必須 |
| FR-12 | 結果表示 | 店名、店ジャンル、品目一覧とジャンル、合計金額、整合性チェック結果を表示する | 必須 |
| FR-13 | 低信頼時の選択UI | 信頼度が閾値未満のとき「未確定」と表示し、候補から選べるようにする | 推奨 |
| FR-14 | 検索失敗時の縮退 | 検索失敗・タイムアウト時は「判定不能」と表示する。キャッシュ済みの店名は検索せず再利用する | 必須 |
| FR-15 | デモ用サンプル | 架空レシート画像をワンクリックで試せるサンプルを用意する | 必須 |

## 5. 非機能要件

| ID | 区分 | 内容 |
|---|---|---|
| NFR-01 | 性能 | 1枚あたりの処理時間を目標10秒以内【暫定】。CPUデプロイ時は30秒以内を許容 |
| NFR-02 | 可用性 | 審査期間中は常時アクセス可能であること（§11） |
| NFR-03 | プライバシー | アップロード画像はディスクに保存せず、ログにも残さない（メモリ上で処理して破棄） |
| NFR-04 | セキュリティ | 認証情報はリポジトリに含めず環境変数で渡す。アップロードにサイズ上限とレート制限を設ける |
| NFR-05 | 再現性 | 学習スクリプトは乱数シード・設定ファイル・依存バージョンを固定し、再実行できること |
| NFR-06 | 可搬性 | docker composeで一式を起動でき、GPU構成とCPU構成を設定だけで切り替えられること |
| NFR-07 | 保守性 | 各段を独立モジュールとして実装し、段単位で差し替え・単体評価ができること |
| NFR-08 | 文書化 | READMEに構成、再現手順、データ出典・ライセンス、モデルの説明を記載する |

## 6. データ要件

### 6.1 データ一覧

| データ | 用途 | 入手元 | 公開可否 |
|---|---|---|---|
| 自分のレシート画像（約100枚、増加中） | 行分類・品目抽出の学習と評価 | 自己収集 | **非公開**（リポジトリに含めない） |
| OCR結果JSON（行テキスト＋座標） | 行分類の学習データ | 上記から生成 | 匿名化・加工後のみ公開可 |
| 品目名テキスト＋ジャンルラベル | 品目ジャンル分類の学習 | 上記＋補強データ | 匿名化後のみ公開可 |
| 店名リスト（有名チェーン・各種業態）＋店概要テキスト＋店ジャンル | 店ジャンル分類の学習 | 公開情報の検索結果 | 店名とラベルのみ公開。スニペット本文は公開しない |
| 合成レシート画像 | 領域抽出の評価／補強、デモ用 | 自作 | 公開可 |

### 6.2 ラベル付け方針

- **行ラベル**: OCR結果に対し、DGX Spark上の大きなLLM／VLMで**事前ラベル付け**し、人間が誤りだけ修正する（蒸留の発想）
- **品目ジャンル**: 同様に事前ラベル付け＋人間修正。手元データが偏るため、補強データで穴を埋める
- **店ジャンル**: 店名リストごとに検索スニペットを集め、事前ラベル付け＋人間修正
- ラベル仕様（ジャンル定義と判断基準）は `docs/label_guide.md` に記録する

### 6.3 データ量の見込み

- レシート100枚 → 行ラベルは千〜二千行規模。行分類・品目分類の学習には足りる見込み
- **レシート単位のラベルは100件しかないため、ここは学習で解かない**（店ジャンル判定とルールで解く）
- 評価は交差検証とし、「100枚での評価なので参考値」と明記する

### 6.4 ライセンス

- 外部データ・検索結果を使う場合は、利用規約・ライセンスを確認し、`docs/data_sources.md` に出典・条件を記録する
- クレジット表記が必要なものはREADMEとスライドに記載する

## 7. モデル要件

| 段 | 名称 | 入力 → 出力 | 手法 | 学習 | 主な評価指標 | 目標【暫定】 |
|---|---|---|---|---|---|---|
| 1 | 領域抽出 | 写真 → 補正済みレシート画像 | OpenCV（輪郭検出＋射影変換）。不十分なら小型セグメンテーション | 原則なし | 抽出成功率（目視） | 90%以上 |
| 2 | OCR | 画像 → 行テキスト＋座標 | 既存の日本語対応OCRモデルを推論利用 | まず無し | 文字誤り率（CER）、金額行の読取正答率 | 金額行95%以上 |
| 3 | 行の役割分類 | 行テキスト＋位置特徴 → 役割ラベル | 軽量なテキスト＋位置特徴の分類器（候補: 日本語BERT系、勾配ブースティング） | あり | macro-F1 | 0.90以上 |
| 4 | 品目の項目抽出 | 品目行 → 名前・個数・単価・金額 | 正規表現・ルール中心。必要なら系列ラベリング | 必要時のみ | 項目単位の正答率、合計整合率 | 整合率80%以上 |
| 5 | 店ジャンル分類 | 店の概要テキスト → 店ジャンル＋信頼度 | ModernBERT系（日本語）のファインチューニング | あり | accuracy、macro-F1 | accuracy 0.85以上 |
| 6 | 品目ジャンル分類 | 品目名 → 品目ジャンル＋信頼度 | ModernBERT系（日本語）のファインチューニング | あり | macro-F1 | 0.80以上 |

### 7.1 判定の流れ（全体ジャンル）

1. 段3の「店名」行から店名を取得し、正規化する（FR-07）
2. 検索で店の概要テキストを取得する（FR-08）
3. 段5の分類器で店ジャンルを判定する（FR-09）
4. 対応表（§8.3）で粒度を決める。**全体で1ジャンル**ならそれを結果とし、**品目ごと**なら段6へ進む（FR-10）

### 7.2 モデル実装の制約

- 推論コードは、transformers、ONNX Runtime、PyTorch等で**モデルを自分のコードにロードして実行**する
- 外部の推論サーバー（Ollama、vLLM等）は、実験・事前ラベル付けでは使ってよい。**デプロイ物の推論には使わない**
- 学習に使ったノートブックとスクリプトは、すべてリポジトリに含める
- 評価指標と目標値は、**学習を始める前に確定**し、`docs/evaluation.md` に記録する

## 8. ジャンル定義【暫定】

> ラベルが確定しないと学習を始められないため、暫定版で開始し、手元データで過不足を見て更新する。**「その他」は必ず用意する**。

### 8.1 店ジャンル（全体用）

飲食店 / 交通（タクシー・鉄道・バス） / スーパー / コンビニ / ドラッグストア / 雑貨・ホームセンター / 医療 / 公共料金・通信 / 衣類・家電 / その他

### 8.2 品目ジャンル

飲料 / 食材 / 菓子 / その他食品 / 日用品 / 雑貨 / 医薬・衛生 / その他

### 8.3 店ジャンル → 判定粒度の対応表

| 店ジャンル | 粒度 |
|---|---|
| 飲食店、交通、医療、公共料金・通信 | 全体で1ジャンル |
| スーパー、コンビニ、ドラッグストア、雑貨・ホームセンター、衣類・家電 | 品目ごとに判定 |
| その他 | 品目ごとに判定（低信頼ならユーザー選択） |

この対応表は設定ファイル（`config/genre_map.yaml`）で管理し、コードに埋め込まない。

## 9. 信頼度と縮退動作

| 状況 | 動作 |
|---|---|
| 分類の信頼度が閾値以上 | 確定として表示 |
| 信頼度が閾値未満 | 「未確定」表示＋候補から選択（FR-13） |
| 検索失敗・タイムアウト | 「判定不能」表示。キャッシュがあれば再利用 |
| 合計の整合性が取れない | 警告を表示し、OCR誤読の可能性を示す |
| 領域抽出に失敗 | 原画像のまま後続へ進む |

閾値は検証データで決める。キャッシュは店名→店ジャンルの対応を保持する。

## 10. 評価計画

1. 学習前に、各段の評価指標と目標値を確定する（§7）
2. レシート100枚を使った**交差検証**を基本とする。同一店舗のレシートが学習と評価に分かれてリークしないよう、**店舗単位で分割**する
3. 段ごとの指標に加え、エンドツーエンドの指標を取る
   - 合計整合率
   - 検索なしで確定できた割合
   - 低信頼でユーザー確認に回った割合
4. 失敗例を分類し、スライドの「つまずいた点」の材料にする

## 11. デプロイ方針【要確認】

要件③は「自分のPCを起動していないとアクセスできない構成は不可」とされており、**DGX Sparkをトンネル公開する構成は文面上グレー**。作り始める前に、講師との1on1で確認する。

### 11.1 1on1での確認事項

1. 自宅の常時稼働サーバー上で推論モデルを動かし、Cloudflare Tunnel経由で公開する構成は、要件③を満たすか
2. 検索結果を外部で取得し、判定は自前のローカルモデルで行う場合、検索APIの利用は補助機能として問題ないか

### 11.2 方針

| 方針 | 概要 | 採用条件 |
|---|---|---|
| **A: 自宅公開型** | DGX Spark上のdocker composeを、Cloudflare Tunnel（＋Cloudflare Access等）で公開 | 1on1で「問題なし」の回答があった場合 |
| **B: クラウド完結型** | CPUで動く軽量モデルをクラウドにデプロイ | 回答が「不可」または「グレー」の場合 |
| **C: 二段構え**（推奨の保険） | 通常はA、停止時はBの軽量構成へ切り替え | A・Bどちらでも対応できるよう設計しておく |

### 11.3 設計への影響

- 構成はdocker composeで束ね、**GPU用とCPU用のプロファイルを設定だけで切り替えられる**ようにする
- Bでは、OCRと分類器をCPUで動く大きさにする。大きなモデルはDGX Sparkでの事前ラベル付けに限定し、**小モデルへ蒸留**する
- モデルの重みはイメージに焼かず、ボリュームまたはHugging Face Hubから取得する

## 12. セキュリティ・プライバシー要件

- **実レシート画像をGitHubに置かない**。デモには架空レシートを使う
- 学習データは匿名化・加工したものだけを公開する。店名、住所、電話番号、カード番号の一部、ポイントカード番号は公開物から除く
- 店舗知識（店名リスト）を公開する場合は、有名チェーンのみにする（行動範囲が推測されるため）
- 検索クエリに含めるのは**店名のみ**とする。レシートの他の情報は外部に送らない
- アップロード画像は保存せず、ログにも残さない
- APIキー・パスワードは環境変数で渡し、`.env`を`.gitignore`に入れる。リポジトリには`.env.example`のみ置く
- 公開エンドポイントには、サイズ上限・レート制限・タイムアウトを設定する（方針Aでは認証も検討）

## 13. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 要件③が満たされない | 修了不可 | 1on1で先に確認。方針Cで保険をかける |
| 審査時に自宅サーバーが停止 | 動作確認不可 | `restart: unless-stopped`、軽量版への自動切替、キャッシュ済みデモ |
| 学習データ不足・偏り | 精度低下 | 事前ラベル付けと補強データ、クラス数を絞る、店舗単位の交差検証 |
| OCR誤読が多い | 下流の精度低下 | 素のOCRでまず測定し、整合性チェックで検出。必要ならOCR側を調整 |
| 検索結果の規約・費用・遅延 | 機能不全 | 規約確認、キャッシュ、検索失敗時の縮退動作 |
| 外部APIに依存して見える | 要件①の疑義 | 判定は自前モデル、検索は補助。説明をスライドに記載 |
| 個人情報の混入 | 公開事故 | コミット前チェック、`.gitignore`、匿名化スクリプト |
| スコープの肥大化 | 未完成 | 端から端までの最小構成を最優先。拡張は余裕があるときのみ |

## 付録: 用語

| 用語 | 説明 |
|---|---|
| OCR | 画像中の文字をテキストに変換する処理 |
| 事前ラベル付け | 大きなモデルがラベル案を出し、人間が誤りだけ修正する手法 |
| 蒸留 | 大きなモデルの判断を教師にして、小さなモデルを学習させる手法 |
| 縮退動作 | 一部の機能が使えないときに、機能を絞って動作を続けること |
| CER | Character Error Rate。OCRの文字誤り率 |
