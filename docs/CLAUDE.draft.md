# CLAUDE.md

このファイルは、本リポジトリで作業するClaude Codeへの開発ルールです。作業前に必ず読み、`docs/requirements.md` と `docs/architecture.md` と合わせて従ってください。

## 1. プロジェクト概要

スマホで撮ったレシート画像から文字起こしを行い、**店ジャンル（レシート全体）**と**品目ジャンル**を自動判定して、Webで表示するアプリ。機械学習コースの最終課題として、「データ準備 → モデル開発 → アプリ組み込み → デプロイ」を一貫して行う。

- フロントエンド: Elixir / Phoenix（LiveView）
- 推論サービス: Python / FastAPI / transformers 等
- 学習・実験: Python（ノートブックとスクリプト）、DGX Spark上で実行
- 構成: docker compose（`gpu` / `cpu` プロファイル）

パイプライン: **領域抽出 → OCR → 行の役割分類 → 品目抽出 → 店名正規化 → 検索 → 店ジャンル分類 → 判定粒度の決定 → 品目ジャンル分類 → 結果表示**

## 2. 最重要ルール（修了要件に直結）

次の項目は、ユーザーの明示的な指示がない限り、変更しないこと。

1. **推論の本体は自前のPythonコードで実行する。** モデルはtransformers、ONNX Runtime、PyTorch等でロードし、前処理・推論・後処理をリポジトリ内のコードで書く
2. **ジャンル判定を外部LLM APIに置き換えない。** OpenAI API、Hugging Face Inference API、クラウドのAIサービスなど、モデルが外部で動く構成は禁止（要件①を満たさなくなる）
3. **外部APIは検索（店情報の取得）のみ。** 補助機能として使い、判定は自前モデルで行う
4. **デプロイ物の推論にOllama・vLLM等の配信サーバーを使わない。** 事前ラベル付けや実験での使用は可
5. **学習に使ったノートブック・スクリプトを削除・移動しない。** 提出時にリポジトリへ含める必要がある
6. 動作確認は「入力 → 推論 → 結果表示」を画面から一通り行えることを基準にする

## 3. 個人情報・セキュリティルール（違反禁止）

- **実レシート画像、およびそれから作ったデータをコミットしない。** `ml/data/private/` は常に `.gitignore` 対象
- 公開してよいデータは、匿名化済みデータ、合成データ、`samples/` の架空レシートのみ。店名・住所・電話番号・カード番号・ポイントカード番号・インボイス番号を含めない
- **検索クエリに含めるのは店名のみ。** 画像やレシートの他の行を外部に送らない
- **アップロード画像を保存しない。** ディスクに書かず、ログにも出さない（メモリ上で処理して破棄）。例外ログにも画像・OCR全文を含めない
- APIキー・パスワード・トークンをコードやリポジトリに書かない。環境変数で渡し、`.env` は `.gitignore` に入れ、リポジトリには `.env.example` のみ置く
- 検索結果のスニペット本文（利用規約上グレー）はリポジトリにコミットしない
- 外部データを追加するときは、ライセンス・利用規約を確認し、`docs/data_sources.md` に出典と条件を記録する
- 新しい依存パッケージを追加するときは、ライセンスと必要性を確認する

## 4. ディレクトリ構成

```text
config/       設定（genre_map.yaml, labels.yaml, thresholds.yaml）
docs/         要件定義・構成図・評価・ラベル仕様・データ出典
ml/           notebooks / scripts / configs / data(private, public)
inference/    FastAPI 推論サービス（src/receipt_app/stages/ に段ごとのモジュール）
web/          Phoenix LiveView
samples/      デモ用の架空レシート
```

- 構成を変えるときは、`docs/architecture.md` も同時に更新する
- ジャンル定義や対応表は**コードに埋め込まず**、`config/` のYAMLで管理する

## 5. 開発コマンド

> 初期セットアップ時に実際のコマンドへ更新すること。

```bash
# 全体起動（GPU: DGX Spark）
docker compose --profile gpu up --build

# 全体起動（CPU: クラウド想定の軽量構成）
docker compose --profile cpu up --build

# 推論サービス（Python）
cd inference
uv sync
uv run ruff check . && uv run ruff format --check .
uv run mypy src
uv run pytest

# Webアプリ（Elixir）
cd web
mix deps.get
mix format --check-formatted
mix credo --strict
mix test
```

## 6. コーディング規約

### 共通

- コード中の識別子は英語、コメント・docstring・コミットメッセージ・ドキュメントは**日本語**
- 1つの関数・モジュールは1つの責務にする。パイプラインの各段は `stages/` に独立モジュールとして実装し、**単体でテスト・評価できる**ようにする
- マジックナンバー（閾値、ラベル名、対応表）を直書きせず、設定ファイルから読む
- 不要な抽象化や過剰な設計を避ける。課題の本質は「ML部分をやり切ること」で、外側のアプリは最小限でよい

### Python（`inference/`, `ml/`）

- Python 3.11以上、型ヒントを付ける。`ruff`（lint・format）と`mypy`を通す
- 設定は pydantic 等で型付きにして検証する
- モデルのロードは**起動時に1回**行い、リクエストごとにロードしない
- 例外は握りつぶさない。外部API失敗は想定内の縮退（「判定不能」）として扱い、原因をログに残す（画像・OCR全文は出さない）
- 公開関数にはdocstring（日本語）を書く

### Elixir（`web/`）

- `mix format` と `mix credo --strict` を通す
- 推論サービス呼び出しは専用モジュールに閉じ込め、タイムアウトとエラー処理を必ず実装する
- 画面は最小限にする（アップロード、結果表示、低信頼時の選択）。UIの作り込みに時間をかけない

## 7. 機械学習ルール

- **学習を始める前に、評価指標と目標値を `docs/evaluation.md` に記載する。** 後から指標を変えて結果を良く見せない
- 乱数シード、依存バージョン、ハイパーパラメータを設定ファイルに固定し、再実行できるようにする
- **評価データは店舗単位で分割する。** 同じ店のレシートを学習と評価に分けない（リーク防止）
- データ量が少ない（レシート約100枚）ため、評価は交差検証で行い、結果は「参考値」と明記する
- 事前ラベル付けにLLMを使った場合、**人間が修正した版を正解**として扱う。修正前後の差分も記録する（工夫点として使える）
- 実験の記録（試したこと、失敗、原因、対処）を `docs/devlog.md` に残す。**提出スライドの「つまずいた点」の材料になる**
- 分類モデルは、まず小さく動かしてから改善する。最初から大きなモデル・複雑な構成にしない
- 学習済み重みはGitにコミットしない（Hugging Face Hubまたはボリュームで管理）。ただし重みの取得方法をREADMEに書く

## 8. 縮退動作と信頼度

- 分類の信頼度が閾値未満のときは「未確定」として返し、UIで候補から選べるようにする
- 検索が失敗・タイムアウトしたときは「判定不能」を返す。**例外でアプリ全体を落とさない**
- 同じ店名は検索せずキャッシュを使う
- 領域抽出に失敗したら、原画像のまま後続へ進む
- 品目金額の合計と合計金額が一致しないときは、警告を結果に含める

## 9. テスト・検証

- 各段にユニットテストを書く（サンプルは `samples/` の架空レシートと合成データを使う）
- 実レシートを使ったテストは、ローカル専用の手動検証とし、**CIやリポジトリに含めない**
- 変更後は、lint・型チェック・テストを実行してから完了報告する
- 「動いた」と報告する前に、実際に画面から入力 → 結果表示まで確認する。確認できていない場合は、その旨を正直に書く

## 10. Git・作業の進め方

- ブランチは機能単位で切る（例: `feat/stage3-line-classifier`）。コミットは小さく、メッセージは日本語で「何を・なぜ」を書く
- コミット前に、`git status` と差分を確認し、**画像・データ・`.env`・重みが含まれていないこと**を確かめる
- 大きな変更や設計の判断が必要なときは、実装前にユーザーへ相談する
- 次の項目は、**必ず事前にユーザーへ確認する**
  - デプロイ方針（A/B/C）の確定と、デプロイ先の選定
  - 検索APIの選定、有料サービスの利用、費用が発生する操作
  - ジャンル定義（`labels.yaml`）の大きな変更
  - 新しい外部サービス・外部APIの追加
  - データの削除や、ブランチ履歴の書き換え
- 不明点は推測で進めず、選択肢と推奨を添えて質問する

## 11. 作業の優先順位

1. **端から端まで動く最小構成**を先に通す（M1）。精度改善はその後
2. 弱い段を特定してから、その段だけを改善する（OCR誤読？分類ミス？）
3. ファインチューニングの主戦場は分類側（行分類・店ジャンル・品目ジャンル）。OCRは素のモデルで測ってから判断する
4. JANコード併用、再学習ループ、一発方式の比較は「余裕があれば」。先に着手しない

## 12. 完了の定義（Definition of Done）

- [ ] 機能が、画面から入力 → 推論 → 結果表示まで動く
- [ ] lint・型チェック・テストが通る
- [ ] 設定値が `config/` にあり、コードに直書きされていない
- [ ] 個人情報・認証情報・実レシート・重みが差分に含まれていない
- [ ] 関連ドキュメント（`docs/`、README）を更新した
- [ ] 実験の場合は、指標と結果を `docs/evaluation.md` と `docs/devlog.md` に記録した
