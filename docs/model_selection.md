# モデルの選定の経緯

レシートの読み取りと品目ジャンルの判定に、最終的にどのモデルを使ったか、そこに至るまでに何を試し、
なぜ選んだかをまとめる。数値の詳細と日々の記録は `devlog.md`、評価の決め方は `evaluation.md` にある。

## サマリー

| 段 | 当初の計画（10/23） | 最終（11/1） | 決め手 |
|---|---|---|---|
| 読み取り（画像 → 店名・品目・金額） | 日本語 OCR ＋ 行の役割分類器 ＋ ルールのパーサ | **Qwen3.6-35B-A3B（NVFP4）** に画像から JSON を直接出させる | 合計整合率 49% → **92%** |
| 店ジャンル | 検索で取った店の概要文を ModernBERT 系で分類（学習あり） | **モデルを使わない**。OpenStreetMap の店種別タグを対応表で変換 | 使える検索 API が無く、OSM のタグで足りた |
| 品目ジャンル | ModernBERT 系をファインチューニング | **Qwen3.6-35B-A3B** に選択肢（enum）から選ばせる。学習なし | 大分類の正解率 58% → **91%** |

- 読み取りと品目ジャンルは、同じ1つのモデル（Qwen3.6-35B-A3B）を DGX Spark 上の vLLM で配信して使う
- どちらも学習はしていない。公開モデルをそのまま（量子化して）使っている。ファインチューニングの候補は `finetuning.md`
- 判断の分かれ目
  - 推論サーバー（vLLM）を使ってよいと確認でき、CPU 前提をやめて Spark の GPU を使えるようになった（10/30）
  - 指標を「品目の合計がレシートの合計と合うか（合計整合率）」に決め、同じ実レシート89枚で全候補を比べた

## 前提の変化: CPU から GPU へ

- 当初は「推論はリポジトリ内の Python でモデルを読み込んで行い、vLLM などの配信サーバーはデプロイ物に使わない」という制約を自分で置いていた。課題の要件の文言とずれて見えることを恐れたため
- このため、最初の OCR の候補は CPU で動くもの（RapidOCR）に絞った
- 10/30 に、公開モデルを自前の環境で動かすことは要件を満たすと確認できた。配信サーバーと量子化モデル（NVFP4 等）も使ってよいことにし、DGX Spark（GB10、統合メモリ128GB）の GPU で大きなモデルを動かす選択肢が開いた
- 外部の推論 API（OpenAI 等）は使わない。外部に送るのは、店の検索に使う店名だけ

## 読み取り

### 1. RapidOCR（PP-OCR）＋ルールのパーサ（10/30 午前）

- RapidOCR（PaddleOCR の ONNX 版、Apache-2.0、CPU で動く）の2つのモデルを3枚で比べた
  - PP-OCRv5 server: 漢字が簡体字になり（証→证、話→话）、片仮名も崩れた（ン→ソ）
  - **PP-OCRv6 medium**: 日本語として正しく読め、ロゴの店名も読めることがあった → 採用
- 読んだ文字の箱を行にまとめ、ルールのパーサで品目と合計を取り出した。行の役割分類器は作らず、まずルールで測った
- 89枚での結果と改善
  - 初回: 合計整合率 20%
  - 行の組み立てを直す（写真の傾きを打ち消し、行全体の平均位置と比べる）: 35%
  - パーサの規則を直す（レジ担当者の番号、住所のハイフン、JAN コードの行のずれ、税の二重計上など）: **49%**
- 残った失敗の多くは OCR の読み誤り（カンマがピリオド、¥ が *、税区分の印が数字に付く）で、パーサで吸収し続けるのは限界があった

### 2. 視覚言語モデル（VLM）の比較（10/30 午後）

GPU を使えるようになったので、OCR を VLM に置き換える案を同じ89枚で比べた。推論は NGC の vLLM 26.10 コンテナ。

- 比べた2つの使い方
  - lines: VLM に行ごとに書き起こさせ、既存のパーサに渡す（OCR だけを置き換える）
  - struct: VLM に店名・品目・金額・合計を JSON で出させる（パーサまで置き換える）

| モデル | 種類 | 方式 | 合計を読めた | 合計整合率 | 1枚（中央値） |
|---|---|---|---|---|---|
| PP-OCRv6 medium ＋ パーサ（それまでの方式） | OCR（CPU） | ― | 76% | 49% | 4〜13秒 |
| Qwen3.5-4B（NVFP4） | 汎用 VLM | lines | 37% | 33% | 7.3秒 |
| Qwen3.5-4B（NVFP4） | 汎用 VLM | struct | 99% | 57% | 5.2秒 |
| GLM-OCR（1.3B） | OCR 専用 VLM | lines | 92% | 76% | 4.4秒 |
| GLM-OCR（1.3B） | OCR 専用 VLM | struct | 98% | 16% | 3.3秒 |
| PaddleOCR-VL-1.6（0.9B） | OCR 専用 VLM | lines | 58% | 25% | 2.7秒 |
| **Qwen3.6-35B-A3B（NVFP4）** | 汎用 VLM（MoE） | lines | 91% | 72% | 10.6秒 |
| **Qwen3.6-35B-A3B（NVFP4）** | 汎用 VLM（MoE） | **struct** | **100%** | **89%** | 7.0秒 |

- モデルごとの傾向
  - Qwen3.5-4B: 「合計」と金額を別の行に書き出すので、パーサが合計を見つけられない。指示文に例を足しても直らなかった
  - GLM-OCR: 項目名と金額を同じ行に正しくまとめて読める（lines で 76%）。ただし JSON への構造化は苦手
  - PaddleOCR-VL: 文字は読めるが、左の列を読み切ってから右の列を読むので、項目名と金額が離れる
  - Qwen3.6-35B-A3B: 総パラメータ35B の MoE で、1トークンあたりに動くのは約3B。大きなモデルの読解力を、小さいモデルに近い速さで使える。struct で最も良かった
- 見送ったもの: 日本語に特化した sarashina2.2-vision-3b
  - vLLM が対応しておらず、transformers で直接動かすと1枚約190秒かかった
  - 文字はよく読めるが、PaddleOCR-VL と同じく項目名と金額が別の行になり、合計のそばの金額も読み落とした
- 確かめたこと: 合計に合わせて品目をでっち上げていないか。GLM-OCR の書き起こしと突き合わせると、品名の91%が一致し、残りも表記の揺れで、金額も一致していた

### 3. 採用: Qwen3.6-35B-A3B（NVFP4）の struct

- 選んだ理由
  - 合計整合率が最も高い（89%）。パーサが要らなくなり、レシートの形式ごとの規則を書き足さずに済む
  - JSON スキーマで出力の形を縛れる（vLLM の構造化出力）ので、壊れた応答がほぼ出ない
  - NVFP4 に量子化した版（RedHatAI 配布、Apache-2.0）で、重み約22GB・1枚約7秒。Spark の上で他と同居できる
  - 品目ジャンルの判定にも同じモデルを使えるので、配信するモデルが1つで済む
- 組み込んだ後の改善（10/31）
  - 税区分の印（「外8」「軽8」）を個数と読む癖があった → 指示文で注意し、単価×個数が金額と合わない個数を規則で1に戻す
  - 品目の直後の割引の行 → 規則で直前の品目にまとめる
  - 合計整合率 89% → **92%**
- 旧方式（RapidOCR＋パーサ）は `stages/ocr_reader/` に残し、`RECEIPT_READER=ocr` で戻せる

## 店ジャンル

- 当初の計画: 検索 API で店の概要文を取り、ModernBERT 系の分類器（学習あり）で店ジャンルにする
- 10/26 に調べると、Bing Search API は終了、Google Custom Search は新規登録不可、残る Brave・Google Places はクレジットカードの登録が必要だった
- 代わりに、登録不要で無料の OpenStreetMap（Nominatim）で店名を検索し、店種別タグ（`shop=convenience` 等）を対応表で店ジャンルに変換した。同名の店が複数ヒットするので多数決で決め、最多票の割合を信頼度にする
- タグがすでに店の種類を表しているので、分類モデルは要らなくなった
- 例外: 調剤薬局はドラッグストアと同じタグ（`amenity=pharmacy`）で登録されていて見分けられないので、品名に「調剤」を含めば医療にする規則を加えた

## 品目ジャンル

### 1. Ruri v3 30m の類似度（学習なし、10/30）

- 当初の計画は ModernBERT 系のファインチューニングだったが、学習データ（品名とジャンルの組）がまだ無いので、まず学習なしで端から端まで通すことにした
- 日本語の埋め込みモデル Ruri v3 30m（Apache-2.0、CPU で動く）で、品名とジャンルごとの見本の品名との類似度を取り、最も近い見本のジャンルにする
- 商品名だけでは種類が分からないもの（酎ハイの商品名、ウイスキーの銘柄など）を外しやすかった

### 2. Qwen3.6-35B-A3B の制約付きデコーディング（学習なし、10/31〜11/1）

- 判定の段を差し替えられるようにしたうえで、読み取りと同じ Qwen3.6 に品名を1つずつ送り、JSON スキーマの enum でジャンルの選択肢以外を出せないようにした（制約付きデコーディング）
- 信頼度は、ジャンル名の部分のトークンの確率の積
- 実レシートの354品目に人が正解を付けて比べた（`evaluation.md`）

| 分類器 | 段数 | 大分類の正解率 | 小分類の正解率 | 1品名あたり |
|---|---|---|---|---|
| Ruri v3 30m | 1段・2段 | 58.2% | 41.5% | 1〜2ms |
| Qwen3.6-35B-A3B | 1段（大分類を直接選ぶ） | 87.9% | ― | 約0.5秒 |
| **Qwen3.6-35B-A3B** | **2段（小分類を選び、大分類に直す）** | **91.2%** | **86.4%** | 約0.55秒 |

- 選んだ理由
  - 大分類の正解率が Ruri より約30ポイント高い。商品名から種類を推し量る知識の差が出た
  - 2段は1段と同じくらいの正解率で、小分類（内訳）も分かる
  - 品目ごとに並べて送るので、1枚あたりの時間の増え方は1秒前後で済む
- つまずき: 温度0でも、問い合わせのたびに判定が揺れた（同じ品名を2回分類すると約1割が変わる）
  - プレフィックスキャッシュを切っても変わらず、GPU の計算（NVFP4 の MoE など）の非決定性とみられる
  - 対処: 同じ品名を3回問い合わせて多数決にした。揺れは約7%に減った。票が割れると信頼度が下がり、画面で人が選び直せる
- 正解ラベルの注意: 下書きを Qwen の2段で付けて人が直したので、Qwen の2段が有利に出ている。下書きのまま直さなかったのは93%

## 今後の候補

- 品目ジャンル: 正解ラベルを学習データにして分類ヘッドを学習する（当初の計画の ModernBERT 系、または Qwen の小さいモデル）
- 読み取り: Qwen3.6-35B の出力のうち合計が合ったものを正解の代わりにして、Qwen3.5-4B を学習させる（蒸留）。詳細は `finetuning.md`
