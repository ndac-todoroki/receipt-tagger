## 2026-10-26 店の検索手段

- 当初は検索APIで店の概要テキストを取り、分類モデルで店ジャンルにする設計だった
- 調べると Bing Search API は2025年に終了、Google Custom Search JSON API は新規登録不可で、残る Brave・Google Places はクレジットカード登録が必要だった
- 対処: 登録不要・無料の OpenStreetMap（Nominatim）で店名を検索し、店種別タグ（`shop=convenience` 等）を対応表で店ジャンルに変換する方式に変えた
- つまずき: 同名の店が複数ヒットし、`landuse=retail` や `highway=footway` も混ざる → 店に関係するカテゴリだけに絞り、ヒットした各タグの多数決で決めて、最多票の割合を信頼度にした

## 2026-10-30 OCRモデルの選定

- 候補: RapidOCR（PaddleOCR の ONNX 版、Apache-2.0、CPUで動く）の PP-OCRv5 server と PP-OCRv6 medium
- 3枚で比べると、v5 server は漢字が簡体字になり（例: 証→证、話→话）、片仮名も崩れた（ン→ソ）。v6 medium は日本語として正しく読め、ロゴの店名も読めることがあった → v6 medium を採用
- 処理時間は DGX Spark の CPU で1枚あたり約4〜13秒
- 残る誤読の癖: 金額のカンマがピリオドになる、¥ が * になる、軽減税率の印（J・軽）が数字に付く → パーサ側で吸収する

## 2026-10-30 品目抽出のベースライン

- 実物を見ると、店名がロゴ画像で文字になっていないレシートが多い。代わりに「事業者名：株式会社〜」の行が文字で入っていることが多いので、これを店名の最優先の候補にした
- ルールのパーサ（日付の行と小計・合計の行で区切る）で89枚を処理した結果:

| 指標 | 値 |
|---|---|
| 合計金額を読めた | 53 / 89（60%） |
| 合計整合（品目の合計 = 小計・合計・合計−外税のいずれか） | 18 / 89（20%） |
| 品目が1つ以上取れた | 67 / 89（75%） |
| 店名の候補が1つ以上出た | 85 / 89（96%） |

- 目標の合計整合率80%には遠い。失敗の内訳を見て改善する

### 改善1: 行の組み立てが崩れていた

- 失敗の内訳を見ると、レシート全体が2〜3行にまとまってしまっているものが多かった
- 原因: 箱を直前の箱とだけ比べていたため、少し傾いた写真で左右の列の箱が交互に並び、少しずつずれながら鎖のように全部つながっていた
- 対処: 箱の上辺の傾きの中央値から写真の傾きを見積もって打ち消し、比べる相手を行全体の平均位置にした。しきい値もロゴなど大きな箱に引きずられないよう箱の高さの中央値から決めた
- 結果: 合計を読めた 60% → 72%、合計整合 20% → 35%、品目が取れた 75% → 83%

### 改善2: 品目と合計の読み取りルール

- 合計が合わないレシートを見て、次の誤りを直した
  - レジ担当者名とレジ番号の行（例: 名前 + 4桁の数字）を品目と読んでいた → 品目の金額の多くに ¥ などの印が付くレシートでは、印の無い数字を金額とみなさない
  - 住所のハイフン（「26-6」）を値引きのマイナスと読んでいた → 語に続くハイフンは符号とみなさない。住所の行は品目にしない
  - 印字の位置のずれで、前の品目の金額が次の品目のJANコードと同じ行に読まれていた → JANの行の金額は直前の品名に付ける
  - 「¥0」が「04」と読まれていた → 0で始まる数字は金額とみなさない
  - 税率ごとの消費税の内訳と「外税額計」を二重に足していた → 合計行があればそれだけを使う
  - 「730円」「¥1,000-」の形や、「合計」が無く「支払金額」だけのレシートに対応した
- 結果: 合計を読めた 72% → 76%、合計整合 35% → 49%

## 2026-10-30 OCR を GPU の視覚言語モデル（VLM）に置き換える検証

- 動機: パーサの残る失敗の多くが PP-OCR の読み誤り。CPU 前提で候補を絞っていたが、Spark の GPU なら大きなモデルを使える
- 比べ方: 同じ89枚で、既存と同じ合計整合率を測る（`ml/scripts/ocr_vlm.py`、`eval_vlm.py`、`serve_vlm.sh`）
  - lines: VLM に行ごとに書き起こさせ、既存のパーサに渡す（OCR だけを置き換える案）
  - struct: VLM に店名・品目・金額・合計を JSON で出させる（パーサまで置き換える案）
- 推論は NGC の vLLM 26.10 コンテナ（vLLM 0.31）。量子化モデルは NVFP4

| モデル | 方式 | 合計を読めた | 合計整合 | 1枚の時間（中央値） |
|---|---|---|---|---|
| PP-OCRv6 medium（CPU、現行） | パーサ | 76% | 49% | 4〜13秒 |
| Qwen3.5-4B NVFP4 | lines | 37% | 33% | 7.3秒 |
| Qwen3.5-4B NVFP4 | struct | 99% | 57% | 5.2秒 |
| GLM-OCR（1.3B） | lines | 92% | 76% | 4.4秒 |
| GLM-OCR（1.3B） | struct | 98% | 16% | 3.3秒 |
| PaddleOCR-VL-1.6（0.9B） | lines | 58% | 25% | 2.7秒 |
| Qwen3.6-35B-A3B NVFP4 | lines | 91% | 72% | 10.6秒 |
| Qwen3.6-35B-A3B NVFP4 | struct | 100% | 89% | 7.0秒 |

- 汎用の小さいモデル（Qwen3.5-4B）は「合計」と金額を別の行に書き出し、既存のパーサが合計を見つけられない。指示文に例を足しても直らなかった
- OCR 専用モデルの GLM-OCR は、項目名と金額を同じ行に正しくまとめて読み、lines で76%。ただし構造化（struct）は苦手
- PaddleOCR-VL は文字は読めるが、左の列を読み切ってから右の列を読むので、項目名と金額が離れる
- Qwen3.6-35B-A3B（MoE、実働3B）の struct が最も良く89%
  - 合計に合わせて品目をでっち上げていないかを、GLM-OCR の書き起こしと品名を突き合わせて確かめた。品名の91%が一致し、残りも表記の揺れ（かぼちゃ／かばちゃ等）で、金額も一致していた
  - ただし整合率は「品目の合計と合計金額が合う」ことしか見ていない。品名の正しさは正解ラベルで別に測る必要がある
- つまずき: Spark のコンテナが2〜3月版のままで、Qwen3.5 の NVFP4 版を SGLang で読み込めなかった。DGX OS を 7.6.0 に更新し、vLLM 26.10 にすると読めた（ドライバ 580 のまま CUDA 13.4 の前方互換モードで動く）
- つまずき: Spark は CPU と GPU でメモリを共有するので、vLLM の起動時のメモリ計測が他プロセスの増減で揺れて失敗する。KV キャッシュ量（`--kv-cache-memory-bytes`）と使用率の上限を固定して回避
- 見送り: 日本語特化の sarashina2.2-vision-3b（利用規約に同意して取得）は、vLLM が対応しておらず transformers で直接動かすしかない。2枚試したところ1枚約190秒かかった。文字はよく読めるが、PaddleOCR-VL と同じく項目名と金額が別の行になり、小計・合計のそばの金額も読み落とした。速さと形式の両面で合わないので、89枚での計測はしなかった
- 判断: 読み取りを Qwen3.6-35B-A3B NVFP4 の struct に置き換えてアプリに組み込む。旧方式は `stages/ocr_reader/` にまとめて残し、`RECEIPT_READER=ocr` で戻せるようにした。ファインチューニングは後回し（候補は `finetuning.md`）

## 2026-11-01 品目ジャンルの2段化と、LLM の分類器の評価

- ジャンルを大分類6個（惣菜・弁当 / 菓子 / 食材 / 飲み物 / その他の食品 / 食品以外）と小分類24個の2段にした。家計簿で「食材を買って自炊したか、出来上がった物を買ったか」を見分けるため
- LLM（Qwen3.6）に JSON スキーマの enum でジャンルを選ばせる分類器を作った（制約付きデコーディング、学習なし）
- 正解ラベル: LLM の2段で下書きし、ユーザーが直した。457品目のうち飲食店・調剤薬局の103品目は全体で1つの会計なので除き、354品目。下書きのままが93%
- ユーザーの指摘から直したこと
  - 調剤薬局も全体で1つの会計にする。OSM では調剤薬局もドラッグストア（welcia など）も amenity=pharmacy が中心で見分けられないので、品名に「調剤」を含めば店ジャンルを医療にする
  - 同じレシートの同じ品名が別のジャンルになっていた（3組）。分類器に渡す前に品名の重複を除く

| 分類器・段数 | 大分類の正解率 | マクロF1 | 小分類の正解率 | 確定の割合（その中の大分類の正解率） | 1品名あたり |
|---|---|---|---|---|---|
| 埋め込み・1段 | 58.2% | 0.490 | — | 34%（85.1%） | 2ms |
| 埋め込み・2段 | 58.2% | 0.490 | 41.5% | 14%（98.0%） | 1ms |
| LLM・1段 | 87.6% | 0.804 | — | 94%（90.3%） | 161ms |
| LLM・2段 | **90.4%** | 0.803 | 85.3% | 94%（92.2%） | 184ms |

- 読み方
  - 参考値（354品目、1回の計測）。LLM・2段は下書きと同じ分類器なので有利に出る
  - 埋め込みは1段と2段で大分類が同じになる。最も近い見本の大分類を選ぶ点は、まとめても変わらないため。違うのは信頼度だけ
  - LLM は埋め込みより大分類で30ポイント高い。1段と2段の差（2.8ポイント）は、下の揺れの大きさと同じくらいで、差があるとは言えない
- つまずき: LLM の判定が、温度0・同じ入力でも問い合わせのたびに揺れる。下書きと今回の計測で354品目中36品目が別のジャンルになった
  - 1件ずつ送っても、同じ品名を20回送ると信頼度が0.50〜0.96で揺れ、ジャンルが入れ替わる品名もあった
  - プレフィックスキャッシュを切っても変わらなかった（1件ずつ送った2回の間で339品名中41が変化）。GPU の計算（NVFP4 の MoE など）が非決定的だとみられる
- 判断: 既定の分類器を LLM・2段にし、揺れへの対処として同じ品名を3回問い合わせて多数決にした（ユーザー確認済み）。測り直した結果

| 分類器・段数（多数決あり） | 大分類の正解率 | マクロF1 | 小分類の正解率 | 確定の割合（その中の大分類の正解率） | 1品名あたり |
|---|---|---|---|---|---|
| LLM・1段 | 87.9% | 0.835 | — | 88%（92.9%） | 493ms |
| LLM・2段 | **91.2%** | 0.872 | 86.4% | 90%（95.9%） | 553ms |

  - 正解率はほぼ変わらない。信頼度は負けた票の分だけ下がるので、確定の割合は少し減り、確定した中の正解率は上がった（92.2% → 95.9%）
  - 揺れ: 同じ339品名を2回分類して変わった数は、1回ずつの問い合わせでは34〜41（10〜12%）、多数決では23（7%）。減ったが無くならない。揺れる品名は信頼度が低く出るので、低信頼時の選択で人が直す前提にする
  - Spark の API に実レシート3枚を送り、品目ごとに大分類まで返ることを確かめた（1枚 5.5〜12.6秒。大半は読み取り）

## 2026-11-01 Cloudflare Tunnel で公開し、セキュリティを見直す

- `https://receipt.otobako.app` で公開した。認証はかけず、同じ相手から1分10件・1日1000件（429）、待っている依頼は10件（503）まで
- つまずき: 移管したばかりのドメインで、手元のネットワークの DNS が「存在しない」を覚えていて開けなかった。トンネルと Cloudflare の DNS（1.1.1.1 で引ける）は正しく、時間をおくと開けた
- 見直しで直したこと
  - Starlette は 1MB を超えるアップロードをディスクの一時ファイルに書き、しかも本体を全部受け取ってから大きさを確かめていた。「画像をディスクに保存しない」に反するので、上限で打ち切ってメモリだけで受け取るようにした
  - 画像の形式を JPEG / PNG / WebP に限り、画素数を確かめてから展開する。壊れた画像は 500 ではなく 415
  - `/docs` と `/openapi.json` を閉じ、他サイトへの埋め込みの禁止などの見出しを付けた
  - app のコンテナを root 以外で動かし、特権を外した
  - HTTP を HTTPS に転送する設定（Always Use HTTPS）をユーザーが Cloudflare でオンにした
